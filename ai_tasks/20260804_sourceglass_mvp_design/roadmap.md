# Sourceglass ロードマップ

一貫した思想: **画像に *実際に記録・埋め込まれている* 情報だけを、事実として提示する。**
バージョンが上がっても「画像の見た目から AI を推測する」機能は永久に追加しない。

Sourceglass は来歴を2つの層で見る。

| 層 | 何を見るか | 消えやすさ | バージョン |
| --- | --- | --- | --- |
| **メタデータ層** | EXIF / XMP / C2PA | ★ 非常に消えやすい（SNS 投稿・リサイズでほぼ消滅） | v0.1 |
| **画素層** | ウォーターマーク（TrustMark 等） | 中程度（再圧縮に耐えるが、強い切り抜き・大幅な加工で壊れる） | v0.2 以降 |

---

## v0.1 — メタデータ層（MVP）

EXIF / XMP / C2PA。詳細は [`implementation_plan.md`](./implementation_plan.md)。

**v0.1 が抱える最大の弱点:** メタデータは容易に除去できる。
「検出されなかった」の情報価値が構造的に低い。→ これを埋めるのが v0.2。

---

## v0.2 — TrustMark（画素層の導入）

### なぜ TrustMark が次なのか

v0.1 の弱点を直接埋めるから。メタデータが剥がれても、画素側に来歴への参照が残る。

さらに重要なのは、**製品思想を一切壊さないこと**。
ウォーターマークのデコードは「AI っぽさの推定」ではなく、
**BCH 誤り訂正が通る形でペイロードを復元できたという離散的な事実**である。
偶然通る確率は無視できるほど低く、確率表示は不要。

### 調査済みの事実（2026-08-04）

| 項目 | 内容 |
| --- | --- |
| リポジトリ | [`adobe/trustmark`](https://github.com/adobe/trustmark) |
| ライセンス | **MIT** |
| JS 実装 | **公式に存在**（`js/`）。**デコード専用**（エンコードは Python のみ） |
| 構成 | `tm_watermark.js`（検出・デコード） / `tm_datalayer.js`（スキーマ・BCH 誤り訂正） |
| 推論 | ONNX。Chromium では **WebGPU を自動使用**（要 secure context） |
| モデル | `decoder_Q`（256px）/ `decoder_P`（224px, square crop）。**リポジトリ非同梱・初回利用時にダウンロード** |
| 出力 | C2PA の **`c2pa.soft-binding`** 形式。アルゴリズム識別子 `com.adobe.trustmark.Q` |
| 誤り訂正 | 2bit で 4 段階（BCH_SUPER / BCH_5 / BCH_4 / BCH_3）。ペイロードは 100 bit |

### 決定事項

**1. モデルは必ず自前ホストする（同一オリジン）**

公式実装は初回利用時にモデルを外部から取得するが、これをそのまま使ってはいけない。
画像自体は流出しないものの、**「誰がいつ Sourceglass を使ったか」が第三者に漏れる**。
`connect-src 'self'` の CSP とも矛盾する。
→ モデルをリポジトリまたはビルド成果物に含め、同一オリジンから配信する。

**2. soft binding は解決しない。ただし説明する（方針 B・確定）**

TrustMark のペイロードは 100 bit の識別子でしかなく、中身を知るには
マニフェストリポジトリへの外部照会が必要 = No network 原則と衝突する。

Sourceglass の態度:

- 「TrustMark ウォーターマークを検出。ペイロード: `0x...`」という**事実は出し切る**
- 「これは C2PA マニフェストへの参照です。解決には外部への問い合わせが必要なため、
  Sourceglass は行いません」と**明示する**
- 必要な人向けに公式ビューアへのリンクを提示する。**クリックするかはユーザーの意思**

→ 制約を隠さず、製品の説明材料に変える。これは Sourceglass の設計思想そのものの表現。

**3. UX が「一撃解析」から「段階的解析」に変わる**

モデルが数十 MB になるため、ページ表示時に読み込んではいけない。

```
[v0.1 の結果画面]
  ...
  ┌──────────────────────────────────────────┐
  │ Watermark check (optional)               │
  │ Downloads a ~XX MB model. Runs locally.  │
  │                       [ Run check ]      │
  └──────────────────────────────────────────┘
```

→ **v0.1 の結果画面に、この「追加チェック」ブロックを差し込む余白を用意しておくこと。**

**4. 「検出されず」の意味が層ごとに違う**

免責文言を層ごとに分ける必要がある。

| 層 | 検出されなかった場合の正しい言い方 |
| --- | --- |
| メタデータ | メタデータは容易に除去できるため、不在は何も証明しない |
| 画素（ウォーターマーク） | 切り抜き・大幅な加工でウォーターマークは壊れる。また、そもそもウォーターマークを入れない生成ツールも多い |

→ v0.1 の `coverage`（何を検査したか）が、ここで効いてくる。

### v0.2 の技術課題

- ONNX Runtime Web の導入（`onnxruntime-web`）。**マルチスレッド版は COOP/COEP による
  cross-origin isolation が必要**。全アセットが同一オリジンなので導入自体は安全だが、
  `_headers` の変更が必要になる
- WebGPU が使えない環境（Safari / Firefox）での WASM フォールバックと実行時間の確認
- 推論は必ず Worker 上で実行（メインスレッドが秒単位で固まる）
- 公式 JS 実装は decode 専用なので、Sourceglass の用途（検査のみ）と完全に一致する

## v0.3 — 未確定（v0.2 のフィードバックを見てから判断）

### 検討中の2案

**案1: Detector プラグイン API の公開**

第三者が自分のウォーターマークデコーダーを Sourceglass に追加できる公開 API を主題にし、
Watermark Anything (WAM) をリファレンス実装第1号として同梱する。

**案2: WAM デコーダーを素直に追加**

当初案どおり WAM を ONNX 変換して組み込む。

### 判断材料（記録しておく）

- **WAM のライセンス（調査済み）:** 最新の事前学習済み重み（SA-1B サブセット学習）は **MIT**。
  論文版の重み（COCO 学習）は **CC-BY-NC**。→ **MIT の方を選べば OSS に同梱可能**
- **ただし WAM は C2PA エコシステムに紐づいていない。**
  TrustMark と違い任意ペイロードを埋める汎用ウォーターマークなので、
  デコードできても「誰かが WAM で何かを埋めた」以上のことは分からない。
  埋め込み側とスキーマを共有していないとユーザーにとって意味を持ちにくい
- → 単体追加の価値は薄く、「拡張の器」として出す方が実益が大きい可能性がある

**v0.2 リリース後に、実際のユーザーの反応を見て決める。**

### v0.3 で同時にやること

- **npm → pnpm workspaces へ移行する**（D-038）。
  エンジンを別パッケージに切り出してモノレポになるタイミングと重なるため、
  「移行」ではなく「構成変更のついで」になり、コストが実質ゼロになる。
  それまでは npm のまま（コントリビューターの導線と、Phase 0 実測の再検証コストのため）

## 将来 — SynthID（上流待ち・blocked）

- Google の SynthID について、**画像用のローカル検出器は現時点で公開されていない**
  （SynthID Detector はゲート付きのポータル提供。OSS 化されているのはテキスト版のみ）
- したがって「公開されたら追加する」という条件付けが正しい。
  **ロードマップには "blocked on upstream" と明記し、実装予定として期待させないこと**
- 公開された場合も、判断基準は v0.2 と同じ:
  1. ライセンスが MIT 系プロジェクトに同梱可能か
  2. モデルを同一オリジンで自前ホストできるか
  3. 外部 API への問い合わせを必要としないか
  → **3 を満たさない（サーバー照会が必須の）検出器は、どれだけ有名でも採用しない。**

---

## バージョンを跨いで守る不変条件

1. 画像・メタデータ・解析結果を外部に送信しない
2. 確率表示をしない / 「AI ではない」と断定しない
3. 検出器を1つ追加するたびに、**その検出器の「検出されず」が何を意味しないか**を必ず書く
4. 外部 API 前提の検出器は採用しない
5. 解析エンジンは UI・DOM に依存しない（CLI / npm パッケージ化の道を塞がない）
